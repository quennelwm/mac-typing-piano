## 有证据的热点

1. **绘制与合成是优先方向。** sample-2s.txt:24起主线程837采样点，42附近的CA事务提交分支有362点，后续能看到路径阴影、高斯模糊、字形绘制、合成；382及835附近直接落入PianoView.draw/render；1236起另有CA::CG::Queue的210采样点。这些嵌套计数不可相加当CPU百分比。源码render在任何绘制都遍历64键，构建路径/颜色/渐变；白键每次重复加入26黑键轮廓裁剪，标签也再做白减黑；浮音动画每次advance将整个view标needsDisplay，draw忽略dirtyRect。它能解释活动时绘制成本，尚不能证明无输入时仍60Hz常转。
2. **Dock轮询有真实采样证据。** sample:980–1094记录dockTick、observeDock、DockWindowVisibilityObserver及WindowServer查询。旧实现每100ms轮询，普通tick读取onscreen窗口清单，每2秒重新发现Dock；即使visibility未变也refresh整个菜单/启动控件/按键状态/面板。查询和无变化UI刷新应分开评估。此证据没有测出它单独占多少CPU。
3. **音频尚非首要CPU证据。** sample:1140–1148，音频IO线程837点中829点在semaphore等待。SamplerAudio.noteOn/off只调用已载入采样器，无逐键资源加载。常驻OutputMeter确实对每个回调逐样本扫描峰值（1024请求buffer、最多8192帧×8通道，try-lock），但本次短栈没有证明它是主要耗时。采样器和SF2可能占常驻内存，当前没有分区内存证据，不能直接说220M主要都是音库。
4. **已有节制措施应保留。** PianoView在浮音与按压motion皆空时停止60Hz timer，隐藏也stopTimer；setSceneVisible和activeMIDI有等值防重复处理。diagnosticsTimer虽然每0.5s唤醒，但测试窗口隐藏即返回。不要把这些已有保护误报为永久60Hz重绘。

## 建议执行顺序与验证

- 先做低风险无变化短路：Dock采样仍保持现有100ms响应，只有可见性/安全状态/目标屏幕/显示状态改变才刷新相应UI；不要每tick重写已关闭菜单的同值状态。将权限预检/启动按钮刷新从所有绘制与按键refresh中拆出，保留权限失效安全定时检查。核对Dock显示/隐藏、unknown恢复、暂停、屏幕切换和权限撤回无回归。
- 优先减少PianoView重复工作：缓存有限的颜色、渐变和静态几何；每帧只计算一次各键变换轮廓；评估按变动键/浮音脏区域重绘，或将可独立动画的逐键材质与浮音层分开。不能缓存一整条不可独立动画位图替代组件，不能破坏透明黑键下白键扣除、标签独立透明、按压与100%透明零残留。缓存须有尺寸/缩放/主题失效规则与容量边界，以免CPU下降换来无界内存。
- 后续再测诊断成本：音频输出meter按需启用或降低峰值检测频率的收益，需同时保留聚合诊断正确性与声学输出；本次不建议先卸载音库/频繁重建引擎，因为会影响首音延迟和尾音。隐藏控制台时可停止诊断timer本身而非持续空唤醒，预期收益较小。
- 下一版在主许可安装后，用相同机器/音源/偏好观察：受控无输入30–60秒、普通打字、短快速多键、菜单打开拖动、Dock来回避让、浮音开/关。分别记录CPU区间、RSS/footprint/线程、首音延迟与尾音，长时30–60分钟才讨论增长趋势。受控阶段不能用本次工作观察均值作严格前后性能胜出结论。

本轮结论：已建立可复核观察基线，定位绘制与Dock刷新为最有证据的优先优化方向；未证明泄漏，未完成优化或低耗验收。菜单两种关闭FAIL的根因也不能由这次非复现场景线程栈定案。
